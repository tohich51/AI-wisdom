## 2. Результат C03

Тест `test_two_personal_identities_receive_real_pkce_tokens_and_one_refreshes`: **1 passed за 0.84 с**.

- Два различных синтетических личных пользователя (изолированные браузерные сессии, один синтетический account_id) каждый проходят реальный вход и обмен одного кода с PKCE на публичном token endpoint.
- Access JWT принимается текущим `TokenVerifier` для audience продукта; тот же подписанный JWT отвергается при несовпадающей ожидаемой аудитории (`audience_mismatch`); subject и account совпадают с созданными.
- Один `refresh_token` погашается один раз; subject и account сохраняются.
- Хелперы обеспечивают точный logout/delete и проверку GET 404 при очистке; коды, токены и ответы провайдера не логируются.

Границы доказательства: полный MCP-сценарий для приглашённых пользователей не заявляется (MCP работает у фактического владельца и ранее), проверки приглашённых участников/A01 нет, MFA не проверяется, сессии в производственной БД приложения не создавались (в Keycloak временно создавались и удалялись только синтетические пользователи), требования по scope не проверяются (`require_scopes=False`), schema не менялась.

## 3. Уточнение по nonce (test-only)

Исходный бриф ошибочно требовал `nonce` в access JWT. По OIDC Core 1.0 nonce относится к ID Token, а не к access token, поэтому в тесте для access JWT корректное ожидание — `expected_nonce=None`. Неудачный прогон `nonce_mismatch` сохранён для разбора причины; отдельной отрицательной регрессией он не считается; проверка nonce в ID token в проде (C07) не менялась.
